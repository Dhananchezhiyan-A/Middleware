## Summary

- **Current cross-tenant database collisions:** none. This is established by the exhaustive zero-row count for Slug owner across all 28 direct tenant-bearing tables, not by assuming unique values.
- **Values that would collide if another populated tenant were later introduced:** tenant-scoped user emails, role names, source codes, destination names, scoring versions, and singleton configs must become globally constrained or receive an explicit merge policy. Current values from My Workspace are: one redacted email, four system role names, source code `meta`, and one dedup config.
- **Globally unique or internal identifiers:** primary `id` keys, the one account `publicId`, API key hash (no rows), and session refresh-token hashes are already guarded by global unique indexes. Actual hashes/public IDs were not disclosed.
- **Non-database conflict:** Redis holds stale failed/DLQ work referencing Tenant IDs and business rows absent from PostgreSQL. It is not a key collision, but it is unsafe to process as normal single-tenant work.
- **Automatic migration decision:** not safe now. A deterministic data-preserving migration can be prepared after the user selects the canonical identity and approves audit/queue handling. This report does not select a tenant.
